# Complete user-facing i18n Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the remaining user-visible application text into the existing English/pt-BR i18n resources without translating internal technical text or user-provided data.

**Architecture:** Keep i18next as the translation boundary. Organize new keys in the existing `canvas`, `panels`, `report`, `lib`, and `guide` namespaces, using `i18n.t()` in library code and `useTranslation()` in React components. Preserve dynamic values through interpolation and keep English as fallback.

**Tech Stack:** React 18, react-i18next, i18next HTTP backend, JSON locale resources, Node test runner, TypeScript, Vite.

---

- [ ] **Step 2: Route display messages through the `lib` namespace**

Use the existing `_t`/i18n pattern for non-React modules:

```ts

  i18n.t(key, { ns: "lib", ...options });

```

Do not translate values such as condition tags, material names, filenames, HTTP status codes, or user-authored notes.

- [ ] **Step 3: Preserve danger-message semantics**

Replace string-prefix detection with a stable translated-message marker or message key/metadata so translating an error does not break `isDangerMsg`. Keep `STALE_TAB_MESSAGE` stable where it is used as a comparison token, and translate only its rendered display value if the existing call path supports that separation.
